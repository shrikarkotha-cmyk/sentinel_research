# V0.12: 50,000-account activation workload and Enhanced grant candidate

## Scope

One bounded, isolated Linux in-process experiment invoked the actual V0.12 activation handler with a temporary SQLite database and ephemeral issuer/device signing keys. There was no socket traffic, external service, real customer, or Steam connection. The test used 50,000 distinct synthetic accounts: 40,000 valid enrollment requests, 5,000 unowned accounts, and 5,000 invalid device proofs. The first 10,000 requests were handled with one worker and the remaining 40,000 with four workers, with the same case proportions. Timing excludes account preparation and includes client-side signature checking in aggregate throughput; per-request handler timing excludes that checking. Phases differ in account cohort and database growth, so they do not isolate the effect of concurrency.

## Observations

| Metric | One worker | Four workers |
| --- | ---: | ---: |
| Requests | 10,000 | 40,000 |
| Elapsed seconds | 21.122 | 97.264 |
| Requests per second | 473.45 | 411.25 |
| Handler p50 ms | 1.805 | 1.797 |
| Handler p95 ms | 3.861 | 35.523 |
| Handler p99 ms | 6.318 | 181.683 |
| Handler maximum ms | 61.212 | 541.400 |
| Correctly authorized | 8,000 | 32,000 |
| Correctly denied | 2,000 | 8,000 |
| Incorrect outcomes | 0 | 0 |

All 40,000 issued licenses passed signature and expected account/device/game/algorithm/offline-field verification. Database final counts: 45,000 synthetic purchases, 40,000 enrolled devices, 40,000 consumed grants, 5,000 unused grants, SQLite integrity_check = ok. Account preparation took 7.163 seconds. There was no server-side 500 response in either cohort. No production credentials were used.

## Interpretation

The larger concurrent phase showed lower observed throughput and higher tail latency. Serialized SQLite write transactions, repeated schema initialization and repeated issuer-key loading are plausible contributors, not measured root causes. Profile before optimizing; repeat matched workloads on reset database snapshots, then compare transaction, key-management and database changes independently. This pilot does not establish support for 50,000 simultaneous connections, production network/TLS behavior, real storefront traffic, hardware-backed clients, or an absence of vulnerabilities. It is an authorization-path test, not a cracking-resistance or game-FPS benchmark.

## Separate Enhanced candidate

A distinct V0.13 laboratory candidate adds an optional enrollment-grant binding to a trusted intended device public key and algorithm. The issuer checks that binding in the transaction before grant consumption. Nine targeted in-process checks passed: incorrect device denial, grant remaining unused, correct device acceptance, signature verification, replay rejection, legacy Standard acceptance, refund rejection, database integrity, and incomplete binding rejection. The existing native runtime and offline license format are unchanged. The storefront has not yet been integrated with authenticated device provisioning; the feature is not hardware attestation, a complete Enhanced tier or a solution to portable-key cloning. No full regression or Windows test was completed for this candidate. The 50,000-account workload above used unmodified V0.12, not this candidate.

## Next steps

Profile the measured bottleneck, repeat matched samples, implement an authenticated device provisioning flow, and evaluate actual platform compatibility and recovery costs. Maintain the separate player-impact disclaimer. Independent reproduction and interpretation remain necessary.
