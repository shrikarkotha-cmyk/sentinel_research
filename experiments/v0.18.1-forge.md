# Forge V0.18.1 developer integration study

Forge adds one C-compatible startup call that resolves the existing player profile and invokes the established license, device and manifest verifier. CMake now installs the public header, runtime, link inputs and an imported target. Product identity and the signed file list still target the internal Starfall Trail workbench.

| Component | Current evidence | Next qualification |
|---|---|---|
| Native SDK | A C consumer compiled and exercised argument diagnostics. A separately configured C++ application on Windows x64 accepted a legitimate offline profile and rejected both a missing license and a changed protected asset. | Repeat the installed-consumer tests on native macOS and Linux. |
| Managed SDK | A Windows CLR host compiled the C# binding and produced the same three outcomes. | Export Unity and Godot .NET projects and test native loading, scene gating and recovery. |
| Unreal | A startup gate and external-module build rules are available in the private engine source. | Compile with Unreal Build Tool and exercise a packaged desktop build. |
| Platform assurance | Windows regression coverage includes a real TPM and a legacy DPAPI profile. Windows 10, Apple Silicon, Intel macOS, SteamOS and Proton remain open for this milestone. | Run the budget-controlled CI matrix, then perform hardware and storefront-specific acceptance. |
| Preservation | A publisher-operated shutdown policy covers offline reinstalls, archive custody, authorized distribution, save migration and recovery. | Demonstrate a preservation edition on clean replacement hardware. |

The Windows release SDK occupied **4,704,458 bytes** in five installed files. Its runtime DLL occupied **4,693,504 bytes**, 1,536 bytes larger than the previously measured V0.18 DLL. These figures include statically linked native crypto. They exclude engines and game assets. Each engine example uses one application-level verification call. The sample C++ entry point uses 17 nonblank lines, the Unity gate 13 and the Godot gate 12. Managed consumers share a 28-line interop binding. Unreal uses a 10-line C++ gate and 24 lines of module rules. No studio onboarding-time study was performed.

The Windows player suite matched all **76 expected outcomes**. License files issued using the V0.18 issuer remained usable with matching pins on both tested providers after the issuer stopped. Across 20 warm paired starts per provider, median launch/verify/quit times were **168.98 to 169.50 ms** for DPAPI and **202.74 to 203.25 ms** for TPM. A single machine and filesystem cache cannot resolve a general sub-millisecond performance change. Prior capacity and graphics experiments were retained as historical evidence.

During testing, an in-process diagnostic probe kept a test DLL mapped and prevented removal of its temporary directory. Running the probe in a short-lived child process resolved the cleanup failure. Four pinned core Python packages were checked against their versioned PyPI release metadata. The check returned no active advisory IDs for those releases. Native dependencies and future advisories need continuing review.

Both protection modes retain automatic storefront handoff, subsequent offline play, supported mods and bound recovery in the owned lab. Independent security assessment, real storefront integration, packaged engine qualification and protection against a modified client remain outstanding. No commercial effectiveness claim follows from these results.

## Independent Linux CI qualification

The November 25, 2026 [Ubuntu 24.04 hosted qualification](https://github.com/shrikarkotha-cmyk/Sentinel_engine/actions/runs/45709829922) completed successfully on engine commit d7e6a47617d0743a8c9cd339f3f4bad23db25f49. Job logs confirm 72/72 portable integration tests, 3/3 native CTest cases, the installed C ABI probe, two invalid-argument checks and all three external C++ consumer outcomes (missing license denied, authorized startup accepted, changed asset denied). The installed SDK totaled 126,305 bytes, including a 119,224-byte shared library; unlike the Windows static-crypto build, this Linux build links system dependencies. The four pinned Python releases returned no active advisory IDs in the scoped check. The workflow YAML error was corrected and the checksum inventory updated before this run. Hosted Linux results do not establish physical TPM, SteamOS, Proton or packaged engine support. Windows and macOS hosted qualification remain separate gates. No release or merge was approved.

## Independent Windows CI qualification

The initial [Windows Server 2022 run](https://github.com/shrikarkotha-cmyk/Sentinel_engine/actions/runs/45710149792) compiled the candidate and reached the SDK and audit tests, but failed the oversized TPM reference regression because provider initialization preceded reference validation on a runner without a usable TPM. The correction validates the existing reference before opening the provider for both public-key retrieval and signing, without changing the regression expectation or allowing a software fallback for an existing hardware identity. The [corrected Windows run](https://github.com/shrikarkotha-cmyk/Sentinel_engine/actions/runs/45711953786) succeeded on engine commit 9290f90fd87176ca845bb2f419f6ed6f6c97f018, completing the Windows audit runner, installed SDK integration, recovery and Vault checks, offline baseline comparison and retirement build. Physical TPM qualification was not requested on the hosted runner. Linux passed on the prior commit; the subsequent native source change is Windows-specific. Hosted macOS and physical platform acceptance remain separate gates.

## Physical acceptance gate and legacy platform scope

The Intel macOS full-suite attempt was blocked before native compilation by the absence of a compatible wheel for the locked cryptography release. The separately scoped native-only rerun completed successfully. Intel macOS is optional legacy support, not a full qualified platform. No core dependency downgrade was made. Windows, Linux and Apple Silicon remain the current hosted qualification targets.

The next acceptance gate is the private V0.18.1 native Windows player build, using the existing lab issuer public anchor and a disposable build signer. Hosted job 45725066344 was requested on engine commit 0e1258a96498ceb873bf461fe461875356b265cd. Its outcome is pending at the time of this entry. The player package excludes issuer material, profiles and licenses; the native package is an internal candidate, not a commercial OS-signed distribution.

Physical testing must retain the previous working installation and existing profile. Check the local credential provider, then verify the candidate against the existing valid offline license without re-enrollment or credential changes. Record the package digest, build commit, provider label, launch outcome and whether the existing license remains unchanged, without publishing private paths, credentials or raw licenses. A provider label is not hardware attestation. Stop on any OS security warning or unexpected profile change; do not bypass platform protections.

For the subsequent controlled performance audit, use the existing paired V0.18 versus V0.18.1 test methodology with identical hardware, scene, resolution, presets and display settings. Report warm startup median and p95 from 20 alternating measured pairs, frame-time distributions and 1% lows, memory and CPU measurements, and limitations of the measurement control. Distinguish renderer-only comparisons from equivalent full gameplay comparisons. Record failed cases rather than discarding them. Keep optional synthetic load testing isolated to owned lab services; no live storefront traffic. Actual Unity, Unreal and Godot exports and SteamOS/Proton acceptance remain unverified. Keep all work on review branches until the owner approves merging.
