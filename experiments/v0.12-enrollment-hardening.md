# V0.12: Enrollment security hardening

Status: clean Linux sandbox tested; Windows build and physical TPM testing pending.

## Objective
Strengthen authorization instead of expanding the game. V0.11 checked the presented public key format but did not require proof of matching private-key possession before enrollment. V0.12 requires domain-separated cryptographic proof, validates request structure and framing, and keeps the existing signed offline license format. Activation responses are bounded and license files are replaced atomically. The local issuer is restricted to loopback. No new recurring network requirement is introduced.

## Observed results
Two native tests and all 75 expected integration and graphical outcomes passed in a disposable Linux build. Nine additional assertions cover missing/incorrect device proofs, duplicate and unexpected request fields, malformed proof encoding, account-context mismatch, legitimate grant availability after rejected requests, signed replay rejection, and concurrent redemption. A four-request concurrency case produced exactly one successful response and three denials. A synthetic P-256 proof was accepted, but this is not a physical TPM or attestation test. Existing authorization, offline gameplay, supported mods, refunds, and graphics regression checks also passed.

## Limitations
A proof establishes key possession, not hardware provenance or ownership of a bearer grant. Grant-to-device binding and authenticated storefront integration remain pending. Linux software credentials remain copyable, and indefinite offline licenses cannot be immediately revoked. No commercial binary tamper-resistance assessment, Denuvo comparison, 50,000-player load test or V0.12 Windows runtime test has occurred. The HTTP issuer is isolated lab infrastructure. No independent security review or commercial-strength claim is made.

## Next research gates
Evaluate non-exportable device storage and recovery on distinct physical devices; authenticate synthetic transaction handoffs more rigorously; assess startup and runtime performance with matched baselines; test bounded concurrency and service failure; develop the reviewed Sentinel Adaptive pipeline. Retain all known limitations in the regression register. Development and documentation were AI-assisted; the researcher should independently reproduce and interpret these results.
